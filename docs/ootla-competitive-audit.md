# Ootla comparison with EliseAI and DashQ

Reviewed 2026-10-31 (Africa/Lagos).

## Conclusion and method

Ootla already has a persistent sales/leasing CRM, native scheduling, applicant and resident records, maintenance, tasks, imports, reporting and controlled AI tools. The largest gap is turning that foundation into a verified, connected operation: real AI inference, email/SMS, telephony, licensed PMS synchronization, screening and signing. More dashboard panels would not close those gaps.

This audit compares inspected Ootla source and local evidence with the vendors' current official product pages and release notes. Competitor entries describe published capabilities, not independently tested performance, universal contract entitlements or features included in every plan. Unconfirmed competitor capabilities are marked accordingly. No comparative conversion percentages, pricing, performance score or certification is inferred.

Ootla evidence: [holistic review](ootla-holistic-review.md), [pending register](ootla-pending-work.md), [activation checklist](ootla-live-activation-checklist.md), and the modules linked below. The demo feature baseline is commit 3452d66653f4b833ebfb63f77476ae0036793c1b. All 719 shared tracked files matched the live checkout before this documentation update; the two intentionally different files were .env.example and ootla.instance.json. This establishes local source parity, not deployment of ootla.ai.

Status meanings:
- **Native:** persistent Ootla workflow exists, independent of a commercial provider.
- **Activation/verification:** transport exists but credentials, authorization or external acceptance are missing.
- **Partial:** useful native functionality exists; the complete competitor workflow does not.
- **Missing:** no functional implementation was found in the inspected application.
- **Excluded/optional:** a competitor capability does not automatically belong in Ootla's agreed scope.

## Competitor capabilities Ootla should not copy under the current brief

- **Payment collection, card holds/capture/releases, refunds and autopay:** DashQ publishes embedded payment functions ([leasing](https://dashq.io/products/leasing), [residents](https://dashq.io/products/residents)). Ootla is deliberately limited to an existing provider handoff and verified read-only status. This is a product boundary, not permission to implement payment execution.
- **AI applicant approval/rejection:** DashQ's [plans](https://dashq.io/plans) advertise rule-based agentic approvals. Ootla requires an approved screening provider, consent and staff decisions. Keep that boundary.
- **Bulk campaigns/marketing platform:** DashQ publishes audience sync and re-engagement campaigns in its [Marketing Hub](https://dashq.io/products/marketing). Ootla is a sales/leads CRM with contextual follow-up, not a bulk email platform.
- **Outsourced staffing:** DashQ publishes managed leasing coverage through [DashForce](https://dashq.io/). Ootla has software assignment/routing, not a staffed leasing service. This is a commercial operating model, not an omitted screen.
- **Archived households:** Their removal was explicitly approved. Co-applicants and linked contacts already work without an active Household feature; do not restore it for competitor checkbox parity.

## Recommended sequence

These are recommendations for later prompts, not features implemented by this audit.

1. Activate the existing customer administrator deliberately, then configure real inventory, staff/property grants and routing. The current Oodler admin invitation is expired. Do not reset/impersonate the account or email it without approval.
2. Close P01 and P05 together: accepted grounded model inference plus a selected, implemented email/SMS transport with authentic inbound threading, consent and actual delivery states. This makes existing reviewed drafts and follow-ups operational.
3. Close P04 with the client's licensed Yardi documentation and a limited-property reconciliation pilot; enable only permitted reads/writes. CSV remains a functional standalone onboarding path.
4. Complete P06/P07 and P10 where the pilot needs verification, signing and renewals. Preserve staff review and verified lease milestones.
5. Use real pilot outcomes to select bilingual support, entry notices, reporting depth or field/mobile work. Defer amenities, a website-builder/ILS product, self-guided hardware, a public API and specialized housing until explicitly requested.

No new feature implementation, paid model use, provider activation, real tenant message or production deployment was performed during this comparison. Both original databases/private configurations remain separate.
